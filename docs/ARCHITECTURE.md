# Architecture

## Goals

Offline-first, fast start-up, testable business logic, no backend, minimal
dependencies, and a codebase a single developer can maintain.

## Layers

```
presentation (features/*/presentation)   widgets only — no business rules
        │ watches / calls
application  (features/*/application)    Riverpod Notifiers & derived providers
        │ uses
data         (data/repositories, models) repositories, immutable models
        │ uses
core         (core/storage, services)    KeyValueStore, ReminderScheduler,
                                         FeedbackService, utils, shared widgets
```

Rules:

- Widgets never touch `SharedPreferences`, the notification plugin or JSON.
- Controllers never import Flutter widgets except value types (`TimeOfDay`,
  `ThemeMode`).
- Repositories are synchronous for reads (in-memory cache) and asynchronous
  for writes; corrupt stored values are discarded, never fatal.
- Infrastructure is injected through providers and overridden in
  `bootstrap.dart` and in tests (`test/helpers/test_helpers.dart`).

## Start-up

`main()` → `bootstrap()`:

1. `PrefsKeyValueStore.create()` and `ContentAssetSource().load()` run in
   parallel while the native splash is visible. JSON parsing happens in a
   background isolate (`compute`).
2. `ProviderScope` overrides the store, the `ContentRepository` and the
   `LocalNotificationService`.
3. After the first frame, `HisnApp` initialises notifications (lazily),
   handles a notification that launched the app, and re-syncs reminders.

If content cannot be loaded, a localized error screen with "retry" is shown.

## State (Riverpod 3)

| Provider | Type | Purpose |
|---|---|---|
| `settingsProvider` | `Notifier<AppSettings>` | theme, language, reading, feedback, onboarding |
| `favoritesProvider` | `Notifier<List<String>>` | favorite ids, newest first |
| `progressProvider` | `Notifier<ReadingProgress>` | today's counts, resume positions, completion history |
| `tasbeehProvider` | `Notifier<TasbeehState>` | tasbeeh count, target, rounds, stats, custom phrases |
| `remindersProvider` | `Notifier<List<Reminder>>` | reminder settings + OS scheduling |
| `categoryProgressProvider(id)` | derived family | completed/total per category |
| `streakProvider`, `dailyDhikrProvider`, `suggestedCategoryProvider` | derived | home dashboard |
| `routerProvider` | `Provider<GoRouter>` | created once; redirect reads settings lazily |

Day boundaries use the device's local midnight (`DayKey`). Progress and
tasbeeh "today" counters roll over on resume and before every write.

## Navigation (go_router)

- `StatefulShellRoute.indexedStack` with five tabs (Home, Adhkar, Tasbeeh,
  Favorites, Settings); each tab keeps its own stack.
- Full-screen routes on the root navigator: `/read/:categoryId?start=`,
  `/search`, `/reminders`, `/about`, `/privacy`, `/sources`.
- `/onboarding` is enforced by a redirect until completed.
- Reminders are exact when `SCHEDULE_EXACT_ALARM` is available, otherwise
  inexact (`LocalNotificationService.scheduleDaily`); all schedules are
  re-created on launch and resume.
- Reminder notifications carry a route payload (`/read/morning` …); only
  `/read/*` and `/home` payloads are accepted.

## Persistence keys

| Key | Content |
|---|---|
| `settings.v1` | `AppSettings` JSON |
| `favorites.v1` | list of dhikr ids |
| `progress.v1` | day key, counts, positions, history (≤120 days) |
| `tasbeeh.v1` | `TasbeehState` JSON |
| `reminders.v1` | list of `Reminder` JSON |

Versioned keys allow future migrations without breaking old installs.

## Content database

`assets/content/adhkar.json` is generated by `tool/content/build_content.py`
from the files in `tool/content/sources/`. See
[CONTENT_GUIDELINES.md](CONTENT_GUIDELINES.md). `ContentRepository` builds
lookup maps, chapter sections and a normalised search index once at start-up.

## Performance notes

- Lists use slivers / builders; the reader uses `PageView.builder`.
- Geometric patterns are painted once inside a `RepaintBoundary`.
- `select` is used where widgets need a single field (e.g. a dhikr's count).
- No network, no heavy images: the only bitmaps are launcher/splash icons.

## Testing

`test/` contains unit, repository, persistence, controller, scheduling and
full-app widget tests (onboarding, reader, favorites, search, tasbeeh, RTL/LTR,
dark mode, clear data, small phone, tablet, 200% text). See
[release/TESTING_REPORT.md](release/TESTING_REPORT.md).
